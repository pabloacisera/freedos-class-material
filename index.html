Sistemas para Intel 8086/8088 en computadoras personales, con interfaz textual y órdenes escritas.

2000–2026

Continuidad

FreeDOS se mantiene como entorno DOS libre para compatibilidad, industria, retrocomputación y enseñanza.

DOS no es un solo sistema

MS-DOS, PC-DOS y DR-DOS compitieron en el mismo ecosistema. MS-DOS se impuso como estándar de facto en las PC compatibles.

FreeDOS nace para conservar compatibilidad con MS-DOS sin depender de una empresa privada.

Qué se conserva

  • Interfaz de línea de comandos.
  • Modelo de 16 bits en modo real.
  • Compatibilidad binaria con software DOS.

Enfatizar que DOS designa una familia, no un único producto. MS-DOS fue el estándar de facto, pero no el único.

Matiz importante: Windows 95 fue un sistema híbrido 16/32 bits y siguió arrancando sobre DOS (IO.SYS/COMMAND.COM). Lo que cambió fue la integración de la GUI, no la desaparición de DOS.

Historia

¿Qué es DOS?

Definición

Disk Operating System: familia de sistemas operativos diseñada para procesadores Intel 8086/8088 y computadoras personales de las décadas de 1970 y 1980.

Modo texto y CLI

En modo nativo no hay interfaz gráfica. La interacción se realiza mediante una Command Line Interface: terminal o consola de comandos.

Monotarea y monousuario

Un solo programa utiliza el procesador en primer plano. No hay hilos, planificador de procesos ni usuarios y permisos diferenciados.

Acceso directo al hardware

El programa puede acceder directamente a memoria, video y periféricos. No existe la mediación y el aislamiento de un sistema moderno.

16 bits y 1 MB

Registros de 16 bits y 640 KB de memoria convencional + 384 KB superiores. El bus de direcciones es de 20 bits.

Consecuencia: no hay protección de memoria ni niveles de privilegio. Todo el software corre al mismo nivel.

Definir DOS con precisión: no es “un sistema operativo viejo” sino una familia con un modelo de ejecución común.

La suma 640 KB + 384 KB = 1 MB. Los 384 KB superiores no son RAM libre continua: incluyen video, BIOS y ROM de adaptadores.

Historia

MS-DOS y el cambio de escenario

1981–1995

MS-DOS · 1981–principios de los 90

  • Nace asociado al IBM PC.
  • Se impone como estándar de la industria.
  • Competidores: PC-DOS y DR-DOS.
  • La GUI se lanzaba manualmente con el comando win.

Windows 95 · punto de inflexión

  • Interfaz gráfica integrada.
  • Multitarea preemptiva para aplicaciones Win32.
  • Evolución hacia un modelo de 32 bits.
  • DOS sigue en el arranque, pero deja de ser el lanzador manual de la GUI.

Matiz técnico: Windows 95 no fue un sistema de 32 bits puro ni eliminó DOS del arranque. Fue un sistema híbrido que conservó IO.SYS y COMMAND.COM.

Para la clase, la consecuencia es concreta: MS-DOS pierde centralidad comercial, pero su ecosistema de software y sus formatos siguen existiendo. FreeDOS aparece para dar continuidad a ese ecosistema.

Evitar la simplificación “Windows 95 mató a DOS”. La transición fue gradual y mantuvo componentes de DOS durante años.

Este matiz explica por qué FreeDOS todavía tiene sentido: la base instalada de software DOS no desapareció con Windows 95.

Historia

FreeDOS: origen y propósito

1994
1994 Jim Hall propone un DOS compatible, libre y de código abierto.

Qué buscaba

  • Compatibilidad con MS-DOS.
  • Una comunidad que mantenga el proyecto.
  • Continuidad para software y hardware heredado.

Licencia

Software libre bajo GNU GPL. No es dominio público: permite usar, estudiar, modificar y redistribuir bajo las condiciones de la licencia, incluso con fines comerciales.

Propósito: preservar un entorno DOS utilizable para compatibilidad, sistemas heredados, retrocomputación y enseñanza, sin depender de una empresa privada.

Corrección respecto del original: FreeDOS no es “dominio público”; es software libre bajo GPL. La diferencia importa para explicar obligaciones de distribución.

La comunidad y la compatibilidad binaria son el criterio central del proyecto, por encima de agregar funcionalidades modernas.

Archivos

Disco, archivos y sistemas de archivos

Conceptos

El disco es almacenamiento bruto. El sistema de archivos aporta el índice y las reglas necesarias para interpretarlo.

Bloques de discoBytes sin estructura
→
ÍndiceUbica cada archivo
→
ReglasNombre, ubicación, seguridad

Sin filesystem

El sistema no sabe dónde empieza ni dónde termina un archivo. Solo ve sectores y bytes.

Para el procesador

Un archivo es solamente una secuencia de bytes. La estructura la aporta el sistema de archivos.

Tres elementos

  • Nombre de archivo o directorio.
  • Ubicación: segmento o clúster.
  • Seguridad: permisos y estado.

Idea central: un file system es un índice más un conjunto de reglas de organización. Sin esas reglas, el hardware no puede reconstruir un archivo.

Separar almacenamiento físico de organización lógica. El disco no “sabe” qué es un archivo; el sistema de archivos construye esa interpretación.

Adelantar que FAT usa una tabla como índice y que NTFS/EXT agregan journaling y permisos.

Archivos

FAT: la tabla como índice

File Allocation Table

Un archivo no siempre ocupa bloques consecutivos. El directorio indica dónde comenzar y FAT señala qué bloque sigue.

Comparación de variantes FAT

Cómo se lee

La entrada de directorio guarda el nombre, el primer clúster y los atributos. La tabla FAT encadena los clústeres restantes mediante punteros.

Precisión: FAT16/FAT32 no usan “sectores de 16/32 bits”. Lo que cambia es el tamaño de las direcciones de clúster: 16 bits en FAT16 y 28 bits efectivos en FAT32.

Mostrar primero las cuatro partes separadas en el disco. Recién después vincular el directorio con el inicio en 2 y la tabla FAT con los saltos 2 → 5 → 9 → 12 → EOF.

FAT32 tiene un máximo de 4 GB por archivo y volúmenes de hasta 2 TB en implementaciones habituales; no un máximo de 16 GB. Se usa en unidades de más de 16 GB sin problema.

Archivos

NTFS y EXT: sistemas con journaling

Sistemas modernos

NTFS

  • Desarrollado por Microsoft a mediados de los 90.
  • Journaling: registra cambios antes de aplicarlos.
  • ACL/ACE: sujeto, permiso y tipo (permite/niega).
  • EFS: cifrado de archivos y directorios.
  • Compresión y soporte para volúmenes y archivos grandes.

EXT

  • Estándar de Linux y Unix.
  • EXT1/EXT2: rápido y robusto, sin journaling.
  • EXT3: incorpora journaling.
  • EXT4: estándar actual; volúmenes de hasta 1 EiB y archivos de hasta 16 TiB.

Journaling: el sistema anota el cambio en un registro antes de ejecutarlo. Si hay un corte, puede recuperar un estado consistente. EFS es cifrado; la compresión es una función separada de NTFS.

Corrección respecto del original: EFS no es compresión, es cifrado. NTFS también ofrece compresión, pero es otra función.

Evitar dar cifras absolutas sin contexto: los máximos dependen de la implementación y del tamaño de clúster. Para la clase alcanza con distinguir FAT (simple, sin journaling) de NTFS/EXT (journaling y permisos).

Arranque

Secuencia de arranque

6 etapas

Desde el firmware hasta el prompt C:\>. La IVT es el hilo común: se crea en la BIOS y se actualiza en cada etapa.

Firmware

BIOS / UEFI

El procesador ejecuta el firmware de la placa. El POST verifica RAM, CPU y dispositivos. La BIOS escribe la IVT en 00000h–003FFh con servicios básicos de pantalla, teclado y disco.

Precisión: en modo real no existe “espacio protegido”. Los drivers y TSR se cargan en memoria reservada, pero sin protección de memoria.

Usar este mapa como columna vertebral de la clase. Cada etapa se puede explicar con la IVT como referencia.

La BIOS llena la IVT con servicios básicos; el kernel la reemplaza y amplía; los drivers y TSR agregan entradas. Al final, el prompt es la interfaz de la shell.

Arranque

Firmware, sector y kernel

Etapas 1–3
1

BIOS / UEFI

  • POST: verificación de RAM, CPU y dispositivos.
  • IVT en los primeros 1 KB de RAM: 00000h–003FFh.
  • Servicios básicos de pantalla, teclado y disco.
2

MBR / VBR

  • La BIOS lee el sector de arranque con INT 13h.
  • El MBR o VBR contiene el código que busca el sistema.
  • FreeDOS usa su propio sector de arranque; también puede intervenir un gestor como GRUB.
3

KERNEL.SYS

  • El kernel se copia a RAM y toma el control.
  • Reemplaza funciones de la BIOS por rutinas propias.
  • Actualiza la IVT con los servicios del sistema operativo.

IVT: tabla de 256 entradas de 4 bytes. Cada entrada contiene un segmento y un desplazamiento; el procesador la consulta cuando se ejecuta una interrupción.

La IVT ocupa exactamente 1 KB: 256 entradas × 4 bytes. Es una tabla de despacho, no un planificador de procesos.

En la etapa 3 el kernel no “hereda” una IVT inmutable: la modifica para exponer sus propios servicios, especialmente INT 21h.

Kernel

Kernel: el mediador

Núcleo

El kernel traduce las operaciones abstractas de las aplicaciones al mundo físico del procesador, la memoria y los dispositivos.

Aplicación
Kernel
Drivers / controladores
Hardware

Procesador

Gestiona las tareas y decide qué código se ejecuta en cada momento.

Memoria

Asigna segmentos a cada programa y evita que uno invada la memoria de otro.

Componentes

Habla con el hardware mediante drivers: audio, red, GPU, almacenamiento. Pueden ser del kernel o propietarios.

Aislamiento y seguridad

Es consecuencia de la mediación. En FreeDOS este aislamiento es mínimo porque todo corre en modo real.

Principio rector: un programa no debería manipular directamente los componentes. El kernel actúa como orquestador entre la instrucción y el hardware.

Matizar: en FreeDOS la mediación existe, pero no hay protección de memoria ni cambio de nivel de privilegio. Es un kernel monolítico simple.

Arquitectura

Modo real: segmento y desplazamiento

16 bits → 20 bits

Los registros son de 16 bits, pero el bus de direcciones necesita 20 bits para acceder a 1 MB. La dirección física se calcula combinando segmento y offset.

Calculadora de dirección

Dirección física 020D1h

(0100h × 10h) + 10D1h = 020D1h

Rango: 00000h–10FFEFh. La dirección puede superar levemente 1 MB por el solapamiento del último segmento.

Segmentos

  • CS: instrucciones.
  • DS: variables.
  • SS: pila.
  • ES: cadenas o memoria de video.

Sin protección

No hay paginación, multiproceso ni niveles de privilegio. El programa puede controlar todo el procesador.

Fórmula: dirección = (segmento × 0x10) + offset. Cada segmento abarca 64 KB porque el offset es de 16 bits.

Recalcar por qué se multiplica por 0x10: un segmento se desplaza cuatro bits a la izquierda antes de sumar el offset. Eso permite direccionar 20 bits con registros de 16.

El ejemplo 0100:10D1 produce 020D1h. Si el resultado supera 0FFFFFh, el procesador puede acceder hasta 10FFEFh por el solapamiento del segmento.

Arquitectura

Mapa de memoria de 1 MB

640 KB + 384 KB

Todo debe funcionar dentro del primer megabyte. Para superar esa limitación se establecieron categorías de memoria.

Convencional

Primeros 640 KB

Es la memoria disponible para DOS y las aplicaciones. La zona que un programa DOS puede usar directamente.

UMB: huecos dentro de upper que se usan para drivers y TSR.

XMS: memoria por encima de 1 MB, accesible mediante HIMEMX.

EMS: ventana paginada en upper; intercambia páginas de memoria.

Corrección: el original dice “XMR”; el término correcto es XMS (Extended Memory Specification). HIMEMX es el driver de FreeDOS que administra esa memoria.

La memoria expandida (EMS) no es lo mismo que la extendida (XMS): EMS usa una ventana en upper y conmuta páginas; XMS accede a memoria por encima de 1 MB.

El comando MEM permite ver el mapa en una sesión real.

Arquitectura

TSR: multitarea simulada

Terminate and Stay Resident

Sin planificador de procesos, la ejecución concurrente se simula con programas que quedan residentes en memoria y esperan una interrupción.

Programa cargado El kernel le asigna un bloque de memoria.
→

→
Termina INT 21h / 4Ch: libera el MCB.
TSR instalado No libera memoria al finalizar.
→
Residente e inactivo Espera una interrupción específica.
→

Ejemplos

  • CTMOUSE.EXE: controlador de mouse.
  • Gestores de discos.
  • Utilidades de captura de pantalla.

No hay paralelismo real: el TSR no se ejecuta al mismo tiempo que el programa activo. Solo reacciona cuando ocurre su interrupción.

La IVT funciona como tabla de despacho para los TSR, no como un administrador de tareas. No hay planificación ni quantum.

La frase del original sobre la IVT como “administrador de tareas” es imprecisa: la IVT solo contiene punteros a rutinas.

Arquitectura

MCB, PSP y programa

Bloque de memoria

Cada aplicación recibe un bloque con tres piezas consecutivas: una frontera, una cabecera y el código real.

MCB

Memory Control Block · 16 bytes

Es el “cartel” del kernel: indica dónde empieza el bloque, cuánto mide y dónde termina. También registra el PSP propietario y si es el último bloque (Z) o hay otro después (M).

MCB: 16 bytes de control.

PSP: 256 bytes de cabecera del programa.

Programa: código, variables y pila.

Precisión: el PSP mide 256 bytes, no 256 bits. Los primeros 256 bytes del segmento están reservados para esa cabecera; por eso los programas .COM comienzan en el offset 100h.

Usar la analogía del original: MCB es el cartel del kernel, PSP es el DNI del programa y el programa es el cuerpo.

Relacionar con DEBUG: al ensamblar en 100h se está dejando libre el PSP. Ese es el motivo técnico del offset inicial.

Arquitectura

Registros x86 de 16 bits

CPU

Los registros son almacenamientos ultra rápidos dentro del procesador. Los de propósito general miden 16 bits y pueden dividirse en dos mitades de 8 bits.

AX · acumulador

Operaciones e interrupciones

Se usa en operaciones aritméticas y como registro principal de las interrupciones. En INT 21h, AH transporta el número de función. Se divide en AH (alto) y AL (bajo).

Segmento

CS código, DS datos, SS pila, ES extra. Apuntan a bloques de 64 KB.

Movimiento y pila

MOV destino, origen copia datos. PUSH y POP manipulan la pila LIFO, usada para guardar estado antes de llamar a una subrutina.

No todos los registros se pueden fraccionar: SP, BP, SI, DI y los de segmento no tienen mitad alta/baja accesible.

Relacionar AX con INT 21h: AH lleva la función y AL suele llevar un parámetro o resultado. En el ejemplo de DEBUG, AH=09h imprime una cadena y DX apunta al texto.

Vigencia

Casos de uso contemporáneos · 2026

Nichos técnicos

La continuidad de FreeDOS no se explica por nostalgia, sino por necesidades concretas donde sus limitaciones se convierten en ventajas.

Actualización de firmware

Herramientas de flashing para placas base, controladoras y almacenamiento. El acceso directo al hardware evita intermediarios y FreeDOS reemplaza a las versiones antiguas de MS-DOS.

Software heredado

CNC, instrumental de laboratorio y sistemas de punto de venta cuya reescritura no es viable. FreeDOS sustituye una licencia de MS-DOS por una alternativa libre.

Sistemas embebidos

Entornos determinísticos, con tiempos de respuesta predecibles y sin la sobrecarga de un planificador multitarea. La ausencia de memoria virtual vuelve el comportamiento auditable.

Preservación y retrocomputación

Entorno libre y legalmente distribuible para ejecutar software y videojuegos de 1981 a mediados de los 90, sobre hardware original o emulado.

Patrón común: compatibilidad, acceso directo al hardware, bajo consumo y comportamiento predecible. No es un reemplazo de Windows o Linux.

Marcar la diferencia entre “usar FreeDOS porque es antiguo” y “usar FreeDOS porque resuelve un problema actual”.

El caso de firmware es el más extendido: muchas utilidades de BIOS/UEFI siguen distribuyéndose como ejecutables DOS.

Vigencia

Límites y valor pedagógico

Balance

Desafíos del proyecto

  • Relevo generacional: pocos colaboradores con conocimiento profundo de modo real y ensamblador x86.
  • Hardware contemporáneo: los fabricantes reducen el soporte de Legacy BIOS en favor de UEFI puro.
  • Percepción pública: la asociación automática con obsolescencia dificulta reconocer sus usos industriales.

Valor pedagógico

  • Modelo simple para enseñar gestión de memoria.
  • Interrupciones y estructuras de control visibles.
  • Arranque completo y trazable.
  • Menos capas conceptuales que un sistema moderno.

Compatibilidad: en equipos muy nuevos puede requerir modo legacy, un hipervisor o un emulador, según las instrucciones disponibles del procesador.

Valor real: FreeDOS permite ver el recorrido de una instrucción y el movimiento de datos dentro del circuito informático sin la complejidad de un sistema multitarea moderno.

No ocultar las limitaciones: el proyecto depende de trabajo voluntario y el soporte de arranque legacy se reduce.

El valor pedagógico es el argumento más fuerte para esta materia: el sistema es pequeño, pero internamente coherente.

01

Compatibilidad antes que innovación

FreeDOS no busca superar a los sistemas modernos. Garantiza continuidad para un ecosistema de software y hardware que quedó sin soporte comercial.

02

Coherencia interna

Modo real de 16 bits, segmento:offset, PSP/MCB, INT 21h y esquemas UMB/XMS/EMS responden a las restricciones del hardware original.

03

Evolución selectiva

La incorporación de FAT32 y direccionamiento LBA muestra adaptación al almacenamiento contemporáneo sin romper la compatibilidad binaria.

04

Vigencia concreta

Firmware, software heredado, embebidos y preservación son necesidades técnicas reales, no curiosidad histórica.

Cerrar con las cuatro ideas y volver al recorrido: historia, archivos, arranque, kernel, arquitectura y prácticas.

Evitar frases motivacionales. La conclusión es técnica: el sistema sigue siendo útil en nichos identificables.

Virtualización

Virtualización y emulación

DOSBox-X

Ambas permiten ejecutar otro sistema, pero no hacen lo mismo. La diferencia está en si comparten la arquitectura del host o si la simulan.

Sistema invitado
Hipervisor
Hardware del host

Qué hace

Ejecuta varias máquinas virtuales sobre los mismos recursos. Requiere instrucciones de virtualización del procesador: Intel VT-x o AMD-V.

El hipervisor puede ser de tipo 1 (cerca del hardware) o de tipo 2 (sobre un sistema operativo).

Ejemplos

  • VirtualBox: tipo 2.
  • KVM: tipo 1 integrado en Linux.
  • QEMU + KVM: alto rendimiento.

Cuándo usarlo

  • VPS y cloud: AWS, Azure, DigitalOcean.
  • Laboratorios, DevOps y CI/CD.
  • Cuando se busca el mayor rendimiento nativo posible.
Aplicación invitada
Sistema invitado
CPU, RAM, BIOS y dispositivos emulados
Traducción / interpretación
Hardware del host

Qué hace

Recrea un hardware completo en software: procesador, memoria, BIOS, sonido y red. Puede ejecutar una arquitectura distinta a la del host.

Traduce cada instrucción y usa buffers en memoria; por eso consume más recursos que la virtualización.

Ejemplo

DOSBox-X: emula el entorno necesario para ejecutar DOS y software de 16 bits.

Cuándo usarlo

  • Arquitecturas cruzadas: Android en Windows.
  • Preservación y prueba de sistemas antiguos.
  • Ingeniería inversa y depuración de firmware.

La diferencia clave: el virtualizador comparte la ISA del host; el emulador simula otra arquitectura. Si el software es de 16 bits y el host es x86 moderno, igualmente se usa emulación por el entorno de hardware y el arranque.

DOSBox-X se usa en las prácticas porque permite montar imágenes, discos y carpetas del host sin instalar FreeDOS en el equipo real.

Práctica 1

Preparar el entorno DOSBox-X

Disco virtual

Crear un disco virtual de 50 MB, instalar FreeDOS y dejar NASM disponible en el PATH.

Secuencia

  1. Crear la imagen de disco con imgmake.
  2. Montarla como C: y montar la carpeta del host como D:.
  3. Copiar FreeDOS, KERNEL.SYS y COMMAND.COM.
  4. Escribir el sector de arranque con sys c:.
  5. Copiar NASM y configurar PATH.
  6. Verificar con nasm -v.

Antes de ejecutar: los comandos se escriben desde la unidad Z: de DOSBox-X. Ajustar las rutas del host a la ubicación real de la carpeta C:\FreeDOS.

imgmake C:\FreeDOS\freedos.img -t hd -size 50

imgmount c C:\FreeDOS\freedos.img -t hdd
mount d C:\FreeDOS
d:
xcopy d:\freedos c:\freedos /s /e
copy d:\kernel.sys c:\
copy d:\command.com c:\
c:
sys c:
md c:\nasm
d:
cd NASM-2~1.05R
xcopy *.* c:\nasm /s /e
c:
set PATH=%PATH%;C:\NASM
nasm -v

No eliminar -fs fat sin motivo: en el montaje de la imagen conviene dejar que DOSBox-X lea la geometría real de la partición.

Si sys c: falla, revisar que KERNEL.SYS y COMMAND.COM estén en la raíz de C: y que la imagen esté montada como disco duro.

Práctica 2

Programa con DEBUG

hola.com

Ensamblar a mano un programa que imprime Hola Mundo!, calcular su tamaño y escribirlo en disco.

C:\> debug
-a 100
xxxx:0100 mov ah, 09
xxxx:0102 mov dx, 0109
xxxx:0105 int 21
xxxx:0107 int 20
xxxx:0109
-e 0109 'Hola Mundo!$'
-r cx
:15
-n hola.com
-w
-q

Por qué empieza en 100h

DEBUG reserva los primeros 256 bytes para el PSP: parámetros de consola, salida de emergencia y tablas temporales. El código comienza después.

Tamaño total

CX = 15h = 21 bytes decimales: 9 bytes de código + 12 bytes de la cadena.

0100B4 010109 0102BA 010309 010401 0105CD 010621 0107CD 010820 010948 010A6F 010B6C 010C61 010D20 010E4D 010F75 01106E 011164 01126F 011321 011424
Código · 9 bytes Cadena ASCII · 12 bytes Total: 21 bytes = 15h

Desglosar el tamaño: mov ah,09 ocupa 2 bytes; mov dx,0109 ocupa 3; int 21 2; int 20 2. Total código: 9. La cadena 'Hola Mundo!$' ocupa 12.

int 20 es la salida histórica. En código nuevo conviene INT 21h / AH=4Ch, pero DEBUG acepta la forma corta.

Práctica 3

Ensamblador NASM

.COM

El mismo programa, ahora en ensamblador: directiva org 100h, impresión por INT 21h y salida por 4Ch.

org 100h

section .text
  mov ah, 09h
  mov dx, msg
  int 21h

  mov ah, 4Ch
  mov al, 00h
  int 21h

section .data
  msg db 'Hola Mundo!', 0Dh, 0Ah, '$'

Compilar y ejecutar

nasm -f bin hola.asm -o hola.com
hola.com

Qué hace cada bloque

  • AH=09h y DX=msg: imprimir cadena.
  • INT 21h: llamar al kernel.
  • AH=4Ch, AL=00h: terminar con éxito.
  • 0Dh, 0Ah: retorno de carro y salto de línea.
  • $: terminador de cadena para DOS.

Formato: org 100h y -f bin generan un .COM que se carga después del PSP. El programa no necesita un encabezado .EXE.

Si NASM no está en el PATH, ejecutar set PATH=%PATH%;C:\NASM o llamar al binario con ruta completa.

La directiva section .data funciona con el formato binario; el mensaje queda en el mismo segmento y mov dx, msg resuelve la dirección.

Práctica 4

Interfaz gráfica con OpenGEM

GUI sobre DOS

OpenGEM es una interfaz gráfica que se ejecuta sobre FreeDOS. No forma parte del kernel: es una capa de software que necesita sus propios archivos y drivers.

Preparación

  1. Montar la ISO FD14BNS.iso en el explorador del host.
  2. Extraer PACKAGES\GUI\opengem en C:\FreeDOS\GUI\opengem.
  3. Montar la imagen de FreeDOS y entrar a D:.
  4. Desmontar C: y montar la carpeta de OpenGEM como C:.
  5. Ejecutar gem.
imgmount d C:\FreeDOS\freedos.img -t hdd -fs fat
d:
mount -u c
mount c C:\FreeDOS\GUI\opengem
c:
gem

Rutas: si OpenGEM no inicia, verificar que la carpeta extraída sea la raíz montada en C: y que la unidad anterior se haya desmontado con mount -u c.

Diferenciar GUI de sistema operativo: OpenGEM es una aplicación que corre sobre DOS, igual que Windows 3.x corría sobre DOS.

Esta práctica sirve para mostrar que FreeDOS puede soportar interfaces gráficas, aunque el sistema base siga siendo de línea de comandos.

Cierre

Conceptos para retener

Repaso

Modelo de ejecución

DOS es monotarea y monousuario, con registros de 16 bits, direcciones de 20 bits y sin protección de memoria.

Almacenamiento

Un file system es índice + reglas. FAT encadena clústeres; NTFS y EXT agregan journaling y permisos.

Arranque

BIOS/UEFI → MBR/VBR → KERNEL.SYS → CONFIG.SYS → COMMAND.COM/AUTOEXEC.BAT → C:\>.

Interrupciones

La IVT es una tabla de despacho. INT 21h expone los servicios del kernel; los TSR esperan su interrupción.

Para practicar: repetir el recorrido en DOSBox-X, verificar el mapa con MEM, armar hola.com con DEBUG y compilar la versión NASM.

Consultas

Repasar los cuatro bloques y abrir preguntas. Si queda tiempo, ejecutar MEM y comparar el mapa con la diapositiva de memoria.

No agregar frases de cierre motivacionales: terminar con los conceptos y las prácticas pendientes.
