Historia

¿Qué es DOS?

Definición

Disk Operating System: familia de sistemas operativos diseñada para procesadores Intel 8086/8088 y computadoras personales de las décadas de 1970 y 1980.

Modo texto y CLI

En modo nativo no hay interfaz gráfica. La interacción se realiza mediante una Command Line Interface: terminal o consola de comandos.

Monotarea y monousuario

Un solo programa utiliza el procesador en primer plano. No hay hilos, planificador de procesos ni usuarios y permisos diferenciados.

Acceso directo al hardware

El programa puede acceder directamente a memoria, video y periféricos. No existe la mediación y el aislamiento de un sistema moderno.

16 bits y 1 MB

Registros de 16 bits y 640 KB de memoria convencional + 384 KB superiores. El bus de direcciones es de 20 bits.

Consecuencia: no hay protección de memoria ni niveles de privilegio. Todo el software corre al mismo nivel.

Definir DOS con precisión: no es “un sistema operativo viejo” sino una familia con un modelo de ejecución común.

La suma 640 KB + 384 KB = 1 MB. Los 384 KB superiores no son RAM libre continua: incluyen video, BIOS y ROM de adaptadores.

Historia

MS-DOS y el cambio de escenario

1981–1995

MS-DOS · 1981–principios de los 90

  • Nace asociado al IBM PC.
  • Se impone como estándar de la industria.
  • Competidores: PC-DOS y DR-DOS.
  • La GUI se lanzaba manualmente con el comando win.

Windows 95 · punto de inflexión

  • Interfaz gráfica integrada.
  • Multitarea preemptiva para aplicaciones Win32.
  • Evolución hacia un modelo de 32 bits.
  • DOS sigue en el arranque, pero deja de ser el lanzador manual de la GUI.

Matiz técnico: Windows 95 no fue un sistema de 32 bits puro ni eliminó DOS del arranque. Fue un sistema híbrido que conservó IO.SYS y COMMAND.COM.

Para la clase, la consecuencia es concreta: MS-DOS pierde centralidad comercial, pero su ecosistema de software y sus formatos siguen existiendo. FreeDOS aparece para dar continuidad a ese ecosistema.

Evitar la simplificación “Windows 95 mató a DOS”. La transición fue gradual y mantuvo componentes de DOS durante años.

Este matiz explica por qué FreeDOS todavía tiene sentido: la base instalada de software DOS no desapareció con Windows 95.

Historia

FreeDOS: origen y propósito

1994
1994 Jim Hall propone un DOS compatible, libre y de código abierto.

Qué buscaba

  • Compatibilidad con MS-DOS.
  • Una comunidad que mantenga el proyecto.
  • Continuidad para software y hardware heredado.

Licencia

Software libre bajo GNU GPL. No es dominio público: permite usar, estudiar, modificar y redistribuir bajo las condiciones de la licencia, incluso con fines comerciales.

Propósito: preservar un entorno DOS utilizable para compatibilidad, sistemas heredados, retrocomputación y enseñanza, sin depender de una empresa privada.

Corrección respecto del original: FreeDOS no es “dominio público”; es software libre bajo GPL. La diferencia importa para explicar obligaciones de distribución.

La comunidad y la compatibilidad binaria son el criterio central del proyecto, por encima de agregar funcionalidades modernas.

Arranque

Secuencia de arranque

6 etapas

Desde el firmware hasta el prompt C:\>. La IVT es el hilo común: se crea en la BIOS y se actualiza en cada etapa.

Firmware

BIOS / UEFI

El procesador ejecuta el firmware de la placa. El POST verifica RAM, CPU y dispositivos. La BIOS escribe la IVT en 00000h–003FFh con servicios básicos de pantalla, teclado y disco.

Precisión: en modo real no existe “espacio protegido”. Los drivers y TSR se cargan en memoria reservada, pero sin protección de memoria.

Usar este mapa como columna vertebral de la clase. Cada etapa se puede explicar con la IVT como referencia.

La BIOS llena la IVT con servicios básicos; el kernel la reemplaza y amplía; los drivers y TSR agregan entradas. Al final, el prompt es la interfaz de la shell.

Arranque

Antes del primer sector: BIOS y POST

Firmware

El arranque es una cadena de eslabones: cada etapa solo sirve para habilitar la siguiente. El primero de todos es el firmware de la placa base.

BIOS

Programa embebido que controla el hardware básico. Está guardado en un chip ROM o flash, no volátil. La evolución de la BIOS se llama UEFI.

CMOS

Memoria de configuración de la placa: fecha y hora, perfil de energía, activación o desactivación de componentes. Se carga al iniciar y condiciona el POST.

POST

Power-On Self-Test: la rutina de verificación inicial. Comprueba que exista memoria y que los dispositivos respondan antes de buscar un sistema operativo.

Los tres trabajos del POST

  1. Verificar la memoria: sin RAM el procesador no puede escribir ni leer el programa de arranque.
  2. Crear la tabla de interrupciones: la IVT ocupa los primeros 1 KB de RAM y tiene 256 entradas de 4 bytes con rutinas básicas de pantalla, teclado y disco.
  3. Comprobar dispositivos: mouse, teclado, CPU, RAM y video. Si algo esencial falla, el arranque se detiene o emite un aviso.

Hilo conductor: la IVT que crea el POST no es la definitiva. El kernel la reemplaza y amplía; los drivers y TSR agregan entradas. Por eso la misma tabla aparece en casi todo el recorrido.

No confundir: BIOS es el firmware que ejecuta el arranque; CMOS es la memoria que guarda su configuración. Son piezas distintas que trabajan juntas.

Usar la analogía del vehículo: la primera marcha no es el viaje, pero sin ella no se mueve. La BIOS no “ejecuta” FreeDOS: prepara el hardware y cede el control.

La fecha y hora de la CMOS es la razón por la que el sistema puede sellar los archivos con fecha incluso antes de que el kernel tenga su propio reloj.

Arranque

MBR, GPT y VBR: dónde vive el bootloader

Sector 0

La BIOS ya verificó el hardware. Ahora busca el dispositivo de arranque y lee su primer sector con INT 13h. Ahí empieza una de dos historias: MBR o GPT.

MBR · Master Boot Record

  • Ocupa los 512 bytes iniciales del disco.
  • Contiene código de arranque y la tabla de particiones.
  • La BIOS lo lee y ejecuta para encontrar la partición activa.
  • Es el esquema tradicional de los sistemas BIOS.

GPT · GUID Partition Table

  • Tabla de particiones con identificadores GUID.
  • Es el esquema habitual de los sistemas UEFI.
  • UEFI la lee y busca el bootloader en una partición EFI.
  • Convive con discos grandes y muchas particiones.

VBR · Volume Boot Record

El MBR revisa qué partición está activa y lee su primer sector: el VBR. Ese mini-programa entiende el sistema de archivos de esa partición gracias a los parámetros guardados en su boot sector. Su objetivo final es encontrar y cargar el KERNEL.SYS.

Reparto de tareas: el MBR elige la partición; el VBR arranca el sistema de archivos de esa partición. Son dos sectores distintos, con dos responsabilidades distintas.

Precisión: MBR no es el sistema de archivos. Es una tabla de particiones más un pequeño código de arranque. La FAT y los archivos viven dentro de la partición, no en el MBR.

Recalcar la cadena: BIOS → MBR → tabla de particiones → partición activa → VBR → kernel. Cada flecha es un salto de control, no una simple lectura.

En la práctica con QEMU se ve el caso BIOS + MBR: por eso se usa fdisk y luego format c:. GPT aparece cuando el equipo arranca con UEFI.

Arranque

Arranque: kernel, configuración y shell

Etapas 3–6

El VBR cargó KERNEL.SYS: el kernel se copia a RAM, reemplaza las rutinas de la BIOS y actualiza la IVT. Después lee la configuración, carga drivers y cede el control a la shell.

1. KERNEL.SYS: se copia a RAM, reemplaza funciones de la BIOS y actualiza la IVT con los servicios del sistema.

2. FDCONFIG.SYS: carga drivers y el administrador de memoria; acá se elige entre JEMM386 y JEMMEX.

3. COMMAND.COM: ejecuta FDAUTO.BAT y muestra C:\>; el sistema queda listo para recibir órdenes.

JEMM386 · el clásico

  • Administra la memoria superior (upper).
  • Por defecto desactiva EMS, la memoria expandida.
  • Puede acceder a memoria extendida mediante otro controlador como HIMEMX.

JEMMEX · dos en uno

  • Reúne en un solo archivo el acceso a la memoria extendida: los 32 MB completos.
  • Administra la memoria superior (upper) y la extendida.
  • Conserva compatibilidad con juegos viejos que esperan EMS o XMS.

Por qué se elige: no es una preferencia cosmética. Un administrador de memoria distinto mueve drivers, TSR y buffers a zonas distintas, y eso decide si un programa grande entra o no en los 640 KB convencionales.

Nombres que conviene fijar: FDCONFIG.SYS cumple el rol de CONFIG.SYS y FDAUTO.BAT cumple el rol de AUTOEXEC.BAT. Son los nombres propios de FreeDOS.

No hace falta memorizar cada directiva. Lo importante es que el alumno vea que la configuración del arranque es una decisión de ingeniería: dónde vive cada driver y cuánta memoria queda para la aplicación.

Relacionar con el mapa de memoria de la sección siguiente: UMB, XMS y EMS son justamente las zonas que estos administradores organizan.

Procesador

Procesador de 16 bits: ciclos y registros

CPU

En FreeDOS la arquitectura es de 16 bits: los registros y las operaciones manejan hasta 16 bits por vez. Esa “mano” condiciona los buses y la forma de direccionar la memoria.

Ciclo y reloj

Los ciclos se ejecutan con un oscilador de cristal de cuarzo integrado en la placa base. Cada pulso obliga al procesador a reaccionar; el tiempo entre pulso y pulso es un ciclo. La unidad de medida es el hertz.

3,5 GHz equivalen a 0,29 nanosegundos. Para un procesador, 1 milisegundo es una eternidad.

Buses

El bus de datos transporta la información que se mueve en cada ciclo. El bus de direcciones indica en qué lugar de la memoria se lee o escribe.

El 8086 tiene un bus de datos de 16 bits; el 8088, de 8 bits. Ambos comparten un bus de direcciones de 20 bits.

Los registros son cajas internas

El procesador guarda allí la información que usará de inmediato. En la próxima diapositiva se detalla cada familia y qué papel cumple en una instrucción.

No confundir: 16 bits describe el ancho de los registros y del bus de datos. El bus de direcciones tiene 20 bits, y por eso el procesador puede llegar a 1 MB.

La analogía de la “mano” sirve: el procesador puede tomar hasta 16 bits por vez, aunque necesite señalar direcciones más grandes. El segmento es el truco para estirar esa mano.

No hace falta profundizar en frecuencias: alcanza con que se entienda que el ciclo es la unidad de tiempo del procesador y que el reloj marca su ritmo.

Procesador

Registros x86 de 16 bits

CPU

Los registros son almacenamientos ultra rápidos dentro del procesador. Los de propósito general miden 16 bits y pueden dividirse en dos mitades de 8 bits.

AX · acumulador

Operaciones e interrupciones

Se usa en operaciones aritméticas y como registro principal de las interrupciones. En INT 21h, AH transporta el número de función. Se divide en AH (alto) y AL (bajo).

Familias de registros

  • Generales: AX, BX, CX, DX.
  • Índices: SI, DI, BP, SP.
  • Segmento: CS, DS, ES, SS.
  • Control: IP y FLAGS.

Movimiento y pila

MOV destino, origen copia datos. PUSH y POP manipulan la pila LIFO, usada para guardar estado antes de llamar a una subrutina.

No todos los registros se pueden fraccionar: SP, BP, SI, DI y los de segmento no tienen mitad alta/baja accesible.

Relacionar AX con INT 21h: AH lleva la función y AL suele llevar un parámetro o resultado. En el ejemplo de DEBUG, AH=09h imprime una cadena y DS:DX apunta al texto.

Procesador

Modo real: segmento y desplazamiento

16 bits → 20 bits

Los registros son de 16 bits, pero el bus de direcciones necesita 20 bits para acceder a 1 MB. La dirección física se calcula combinando segmento y offset.

El problema: el procesador solo mueve 16 bits por ciclo y necesita guardar un dato en memoria, pero el chip de memoria exige 20 bits para activarse. La solución: el procesador desplaza 4 bits el segmento y suma el offset. Ese desplazamiento es la multiplicación por 10h.

Calculadora de dirección

Dirección física 020D1h

(0100h × 10h) + 10D1h = 020D1h

Rango: 00000h–10FFEFh. La dirección puede superar levemente 1 MB por el solapamiento del último segmento.

Segmentos

  • CS: instrucciones.
  • DS: variables.
  • SS: pila.
  • ES: cadenas o memoria de video.

Sin protección

No hay paginación, multiproceso ni niveles de privilegio. El programa puede controlar todo el procesador.

Fórmula: dirección = (segmento × 0x10) + offset. Cada segmento abarca 64 KB porque el offset es de 16 bits.

Recalcar por qué se multiplica por 0x10: un segmento se desplaza cuatro bits a la izquierda antes de sumar el offset. Eso permite direccionar 20 bits con registros de 16.

El ejemplo 0100:10D1 produce 020D1h. Si el resultado supera 0FFFFFh, el procesador puede acceder hasta 10FFEFh por el solapamiento del segmento.

Kernel

Kernel: el mediador

Núcleo

El kernel es el mediador entre las aplicaciones y el hardware. No “hace todo”: ofrece servicios, coordina recursos y delega lo específico en los drivers.

Aplicación
Kernel
Drivers / controladores
Hardware

API de servicios: expone llamadas como INT 21h para abrir archivos, leer teclado o escribir en pantalla.

Archivos y directorios: interpreta nombres, recorre la FAT y pide los clústeres al driver de disco.

Memoria: asigna bloques, ajusta los MCB y controla qué programa es dueño de cada segmento.

Carga de programas: lee el ejecutable, arma el PSP y transfiere el control al código del programa.

Drivers: traduce pedidos lógicos en operaciones concretas para cada dispositivo.

Buffers y caché: usa memoria intermedia para no leer o escribir el disco en cada operación.

Puente 1 · BIOS: reutiliza INT 10h, INT 13h e INT 16h para video, disco y teclado.

Puente 2 · puertos: escribe y lee con IN/OUT cuando el dispositivo se controla por puertos de E/S.

Puente 3 · interrupciones: recibe IRQ del hardware y registra rutinas en la IVT para atenderlas.

Límite de FreeDOS: la mediación existe, pero no hay protección de memoria ni niveles de privilegio. Es un kernel monolítico y todo corre en modo real.

Principio rector: un programa no debería manipular directamente los componentes. El kernel actúa como orquestador entre la instrucción y el hardware.

Matizar: en FreeDOS la mediación existe, pero no hay protección de memoria ni cambio de nivel de privilegio. Es un kernel monolítico simple.

Discos

Disco: sectores, clústeres y slack

Almacenamiento

Para el sistema, un disco es un conjunto de bloques numerados. Antes de hablar de archivos hay que distinguir tres unidades: sector, clúster y archivo.

SectorBloque mínimo físico · 512 bytes
→
ClústerGrupo de sectores contiguos
→
ArchivoUno o más clústeres encadenados

Sector

Es la unidad mínima que el disco entrega. En los discos de la época de DOS suele ser de 512 bytes.

Clúster

Es un grupo de sectores contiguos. Es lo mínimo que el sistema operativo le reserva a un archivo; también se llama unidad de asignación.

Slack

Es el espacio desperdiciado dentro del último clúster de un archivo. Si el clúster es de 2 KB y el archivo ocupa 0,8 KB, sobran 1,2 KB que no se reutilizan.

Por qué importa: el tamaño del clúster es una decisión de compromiso. Clústeres grandes hacen crecer el slack; clústeres pequeños multiplican las entradas de la FAT y el trabajo del sistema.

Para la práctica: cuando formateás un disco, el sistema elige un tamaño de clúster según el tamaño del volumen. Ese valor explica cuánto espacio real consume una carpeta con muchos archivos chicos.

Usar la analogía de la caja: el sector es la caja mínima, el clúster es la caja en la que el sistema entrega el pedido y el slack es el aire que sobra dentro de esa caja.

No confundir sector con clúster: FAT no direcciona sectores, direcciona clústeres. La relación entre ambos queda guardada en el boot sector del volumen.

Discos

Disco, archivos y sistemas de archivos

Conceptos

El disco es almacenamiento bruto. El sistema de archivos aporta el índice y las reglas necesarias para interpretarlo.

Bloques de discoBytes sin estructura
→
ÍndiceUbica cada archivo
→
ReglasNombre, ubicación, seguridad

Sin filesystem

El sistema no sabe dónde empieza ni dónde termina un archivo. Solo ve sectores y bytes.

Para el procesador

Un archivo es solamente una secuencia de bytes. La estructura la aporta el sistema de archivos.

Tres elementos

  • Nombre de archivo o directorio.
  • Ubicación: segmento o clúster.
  • Seguridad: permisos y estado.

Idea central: un file system es un índice más un conjunto de reglas de organización. Sin esas reglas, el hardware no puede reconstruir un archivo.

Separar almacenamiento físico de organización lógica. El disco no “sabe” qué es un archivo; el sistema de archivos construye esa interpretación.

Adelantar que FAT usa una tabla como índice y que NTFS/EXT agregan journaling y permisos.

Discos

Partición, formateo y asignación

Tres pasos

Una partición no es una carpeta: es una división lógica del disco. Para que DOS pueda usarla hay que completar tres operaciones distintas.

1. ParticiónAnotar inicio y fin en el MBR
→
2. FormateoCrear el sistema de archivos
→
3. AsignaciónDarle una letra de unidad
1

Partición o volumen

Se escribe en la tabla de particiones que el disco empieza en una sección y termina en otra. El MBR conserva ese índice.

2

Formateo

Se establece un sistema de archivos: boot sector, tablas FAT vacías, directorio raíz y tamaño de clúster. La “caja negra” pasa a tener estructura.

3

Asignación

Se le da una letra a ese espacio para diferenciarlo de otros: C:, D:, E:. La letra es una referencia lógica, no el disco físico.

Precisión: formatear no borra físicamente todos los datos. Reescribe las estructuras lógicas que los ubican. Por eso una recuperación todavía es posible hasta que esos sectores se sobrescriben.

Insistir en la separación: partición es geometría lógica, formateo es sistema de archivos y asignación es nomenclatura. Mezclar los tres pasos es el error más común al explicar el almacenamiento.

Relacionar con la práctica de QEMU: después de crear la partición hay que reiniciar la máquina virtual y recién entonces ejecutar format c: y format d:.

FAT: la tabla como índice

File Allocation Table

Un archivo no siempre ocupa bloques consecutivos. El directorio indica dónde comenzar y FAT señala qué bloque sigue.

VarianteEntradas de clústerArchivo máx.Uso típico

Precisión: FAT16/FAT32 no usan “sectores de 16/32 bits”. Lo que cambia es el tamaño de las direcciones de clúster: 16 bits en FAT16 y 28 bits efectivos en FAT32.

Mostrar primero las cuatro partes separadas en el disco. Recién después vincular el directorio con el inicio en 2 y la tabla FAT con los saltos 2 → 5 → 9 → 12 → EOF.

FAT32 tiene un máximo de 4 GB por archivo y volúmenes de hasta 2 TB en implementaciones habituales; no un máximo de 16 GB. Se usa en unidades de más de 16 GB sin problema.

Discos

Ciclo de vida de un archivo en FAT

Crear · leer · borrar

Un archivo no se guarda de una sola vez: el sistema negocia con la FAT, el directorio y el área de datos. Recorramos el ciclo completo de una operación cotidiana.

Crear y escribir

  1. Buscar en la FAT los clústeres libres (marcados con 0).
  2. Encadenarlos: el 5 apunta al 6, el 6 al 7, hasta el final.
  3. Escribir los datos en esos clústeres.
  4. Crear la entrada de directorio con nombre, atributos, fecha y tamaño.
  5. Actualizar ambas copias de la FAT para mantener el respaldo sincronizado.

Leer

  1. Buscar el nombre en el directorio.
  2. Leer el primer clúster indicado en la entrada.
  3. Consultar en la FAT cuál es el siguiente clúster.
  4. Repetir hasta encontrar la marca de fin de archivo.
  5. Entregar los datos al programa que hizo el pedido.

Borrar

  1. Marcar la entrada de directorio como libre.
  2. Poner en 0 las entradas de la FAT que formaban la cadena.
  3. No sobrescribir necesariamente el contenido del clúster.
  4. Dejar esos clústeres disponibles para una escritura futura.

Idea central: la FAT es un índice, no el contenido. Crear, leer y borrar son operaciones sobre ese índice y sobre el directorio; el área de datos se toca después.

Consecuencia práctica: en FAT, borrar no garantiza confidencialidad. El contenido puede recuperarse hasta que otro archivo sobrescriba esos clústeres. Para borrar de verdad hay que sobrescribir.

Corregir la idea de que “borrar escribe ceros” en toda la cadena. Lo que se vacía es la entrada de directorio y las entradas FAT; el contenido del clúster queda hasta que se reutiliza.

Conectar con la práctica: CHKDSK revisa la consistencia entre FAT y directorios; los “clusters perdidos” son cadenas que ya no pertenecen a ningún archivo.

Sistemas modernos

NTFS

  • Desarrollado por Microsoft a mediados de los 90.
  • Journaling: registra cambios antes de aplicarlos.
  • ACL/ACE: sujeto, permiso y tipo (permite/niega).
  • EFS: cifrado de archivos y directorios.
  • Compresión y soporte para volúmenes y archivos grandes.

  • Estándar de Linux y Unix.
  • EXT1/EXT2: rápido y robusto, sin journaling.
  • EXT3: incorpora journaling.
  • EXT4: estándar actual; volúmenes de hasta 1 EiB y archivos de hasta 16 TiB.

Memoria

Mapa de memoria de 1 MB

640 KB + 384 KB

Todo debe funcionar dentro del primer megabyte. La memoria se organiza en segmentos de 64 KB y párrafos de 16 bytes; sobre esa base se definen las categorías del mapa.

RAM: memoria de trabajo volátil; guarda programas, datos, pila y buffers mientras la máquina está encendida.

Segmento: ventana de 64 KB. DOS direcciona la memoria como segmentos, no como una tira continua.

Párrafo: unidad de 16 bytes; por eso un segmento abarca 64 KB (1000h párrafos).

Convencional

Primeros 640 KB

Es la memoria disponible para DOS y las aplicaciones. La zona que un programa DOS puede usar directamente.

00000hTabla de interrupciones · 1 KB
00400hÁrea de datos de la BIOS
0A0000hMemoria de video · B8000h para texto
100000hHMA y memoria extendida (XMS)

Corrección: el original dice “XMR”; el término correcto es XMS (Extended Memory Specification). HIMEMX es el driver de FreeDOS que administra esa memoria.

La memoria expandida (EMS) no es lo mismo que la extendida (XMS): EMS usa una ventana en upper y conmuta páginas; XMS accede a memoria por encima de 1 MB.

El comando MEM permite ver el mapa en una sesión real.

Memoria

MCB, PSP y programa

Bloque de memoria

Cada aplicación recibe un bloque con tres piezas consecutivas: una frontera, una cabecera y el código real.

MCB

Memory Control Block · 16 bytes

Es el “cartel” del kernel: indica dónde empieza el bloque, cuánto mide y dónde termina. También registra el PSP propietario y si es el último bloque (Z) o hay otro después (M).

MCB: 16 bytes de control.

PSP: 256 bytes de cabecera del programa.

Programa: código, variables y pila.

Precisión: el PSP mide 256 bytes, no 256 bits. Los primeros 256 bytes del segmento están reservados para esa cabecera; por eso los programas .COM comienzan en el offset 100h.

Usar la analogía del original: MCB es el cartel del kernel, PSP es el DNI del programa y el programa es el cuerpo.

Relacionar con DEBUG: al ensamblar en 100h se está dejando libre el PSP. Ese es el motivo técnico del offset inicial.

Memoria

Cómo DOS asigna memoria: 48h y 4Ah

INT 21h

DOS no asigna memoria fina por variable: entrega bloques. El programa nace con toda la torta y, si le sobra, devuelve una parte para que otros puedan usarla.

1. El kernel entrega todo Al iniciar un programa, le da el bloque libre completo: por ejemplo, 500 KB.
→
2. El programa se mide Calcula lo que necesita: 40 KB de código y 10 KB de variables.
→
3. Llama a 4Ah Pide al kernel que achique su bloque de 500 KB a 50 KB.
→
4. El kernel ajusta Edita el MCB que ya vimos y marca los 450 KB restantes como libres.

48h · reservar memoria

El programa pide un bloque y el kernel busca segmentos libres recorriendo la tabla de MCB. La reserva se registra con dirección y tamaño.

4Ah · cambiar el tamaño

El programa devuelve la parte que no usa. El kernel corta el bloque, actualiza la etiqueta del MCB y libera el resto para otra aplicación.

La analogía de la torta: el kernel te da toda la torta cuando arrancás; vos, como programa, llamás a 4Ah para quedarte con una porción y devolver el resto a la mesa.

Quién hace cada paso: el pedido de ajuste lo hace el programa, no el kernel. Por eso un programa mal escrito puede pedir de más, no devolver lo que sobra o liberar mal su bloque.

Recalcar la diferencia entre 48h y 4Ah: 48h pide memoria; 4Ah cambia el tamaño de un bloque ya asignado. No son dos formas de reservar, son dos momentos del mismo ciclo.

Relacionar con el MCB: la operación no mueve bytes, edita la etiqueta administrativa. Los datos del programa quedan donde estaban.

Memoria

TSR: multitarea simulada

Terminate and Stay Resident

Sin planificador de procesos, la ejecución concurrente se simula con programas que quedan residentes en memoria y esperan una interrupción.

Programa cargado El kernel le asigna un bloque de memoria.
→
En ejecución activa Ocupa la totalidad del procesador.
→
Termina INT 21h / 4Ch: libera el MCB.
TSR instalado No libera memoria al finalizar.
→
Residente e inactivo Espera una interrupción específica.
→
Rutina de manejo Se ejecuta momentáneamente y retorna con IRET.

Ejemplos

  • CTMOUSE.EXE: controlador de mouse.
  • Gestores de discos.
  • Utilidades de captura de pantalla.

No hay paralelismo real: el TSR no se ejecuta al mismo tiempo que el programa activo. Solo reacciona cuando ocurre su interrupción.

El TSR no crea un proceso nuevo: se cuelga de una interrupción y queda residente. No hay planificación ni quantum.

La frase del original sobre la IVT como “administrador de tareas” es imprecisa: la IVT solo contiene punteros a rutinas.

Memoria

IVT e INT 21h

Interrupciones por software

La Interrupt Vector Table (IVT) es la tabla que le dice al procesador a qué rutina saltar cuando ocurre una interrupción. Sin ella, una llamada como INT 21h no tendría destino.

Qué es y por qué importa

Ocupa los primeros 1 KB de RAM (00000h–003FFh): 256 entradas de 4 bytes. Cada entrada guarda la dirección segmento:offset de una rutina. El procesador la consulta para despachar la interrupción.

Durante la BIOS

El POST la llena con rutinas del firmware: INT 10h para video, INT 13h para disco y INT 16h para teclado. Son los servicios mínimos para arrancar y cargar el sistema.

Cuando la toma el kernel

DOS reemplaza o amplía entradas: INT 21h pasa a apuntar a sus servicios, INT 20h a la salida de programas y los drivers/TSR agregan sus rutinas. Las entradas de la BIOS pueden seguir disponibles.

El programa prepara la llamada

El programa coloca en AH el número de función que necesita. Para crear un archivo usa 3Ch; los parámetros adicionales van en otros registros.

Recorrer el flujo con un ejemplo concreto: guardar una partida. El programa no habla con los cables del disco; llama a INT 21h y el kernel hace el trabajo.

En DOS no hay cambio de modo usuario a kernel: todo corre al mismo nivel. Por eso una interrupción de software es suficiente para exponer los servicios.

Controladores

Controladores: traductores entre kernel y hardware

Drivers

El kernel no puede conocer todos los dispositivos del mundo. Delega en un driver: un programa que sabe comunicarse con un dispositivo concreto.

Controladores de carácter

Manejan flujos de caracteres. Ejemplos: teclado, pantalla, impresora y puerto serie. El sistema lee o escribe una secuencia, no un bloque completo.

Controladores de bloque

Manejan dispositivos de almacenamiento en bloques. El disco entrega sectores numerados y el driver traduce el pedido a esa geometría.

Anatomía de un driver

  • Una cabecera con un puntero al siguiente driver: todos forman una lista encadenada.
  • Un nombre que lo identifica.
  • Dos puntos de entrada: estrategia (recibe el pedido) e interrupción (lo ejecuta y avisa cuándo terminó).
KERNEL.SYSPunto de partida
→

Cómo se conecta: el driver se instala durante el arranque y actualiza la IVT que ya vimos. Cuando llega su interrupción, el procesador salta a la rutina registrada y luego vuelve con IRET.

No confundir: “carácter” describe el modo de transferencia, no el contenido. Un driver de carácter puede transportar texto, comandos o cualquier flujo de bytes.

Comparar con el mundo actual: un driver de impresora no “sabe imprimir”, sabe traducir el pedido del sistema al lenguaje del dispositivo.

La lista encadenada es una estructura muy de la época: cada driver conoce la dirección del siguiente. Si un driver queda mal instalado, puede romper la cadena y afectar a los demás.

Integración

Ejemplo integrado: qué pasa cuando copiás un archivo

De la orden al disco

Reunamos todo: shell, IVT, kernel, FAT, memoria y video en una sola operación cotidiana. Al escribir COPY ORIGEN.TXT DESTINO.TXT ocurre esta película.

1

Shell y llamada al sistema

COMMAND.COM interpreta la orden, prepara los registros de 16 bits con el pedido y dispara INT 21h. El procesador consulta la IVT para encontrar la rutina del kernel y salta hacia allí.

2

Búsqueda y lectura

El kernel lee los registros, busca ORIGEN.TXT en el directorio y consulta la FAT para saber en qué clústeres está. Pide al disco esos clústeres por puertos IN/OUT o con INT 13h; el disco avisa por IRQ y los datos se copian a un buffer en RAM.

3

Escritura y actualización

El kernel busca clústeres libres en la FAT, los encadena hasta el fin de archivo y copia el contenido desde RAM al disco. Después actualiza las dos FAT y crea la entrada de directorio de DESTINO.TXT con nombre, fecha, tamaño y primer clúster.

4

Retorno y confirmación

El kernel deja el resultado en los registros y devuelve el control a COMMAND.COM. El shell escribe el mensaje en la memoria de video (B8000h) con ayuda de INT 10h y el monitor muestra 1 file(s) copied.

Todo el temario en una operación: arranque, shell, kernel, drivers, MCB, segmento:offset, FAT, interrupciones y memoria de video aparecen conectados. Esta diapositiva es el mapa para volver cuando una pieza aislada no cierre.

Recorrer la imagen de izquierda a derecha, franja por franja. Después volver a las diapositivas de IVT, FAT y MCB para mostrar dónde vive cada pieza del ejemplo.

Si surge la duda: el kernel no “copia” directamente del disco al disco. Siempre pasa por un buffer en RAM. Ese detalle es el que conecta almacenamiento con memoria.

Aclarar que el diagrama simplifica el polling, la caché y el manejo de errores: lo importante es el orden conceptual.

Vigencia

Casos de uso contemporáneos · 2026

Nichos técnicos

La continuidad de FreeDOS no se explica por nostalgia, sino por necesidades concretas donde sus limitaciones se convierten en ventajas.

Actualización de firmware

Herramientas de flashing para placas base, controladoras y almacenamiento. El acceso directo al hardware evita intermediarios y FreeDOS reemplaza a las versiones antiguas de MS-DOS.

Software heredado

CNC, instrumental de laboratorio y sistemas de punto de venta cuya reescritura no es viable. FreeDOS sustituye una licencia de MS-DOS por una alternativa libre.

Preservación y retrocomputación

Entorno libre y legalmente distribuible para ejecutar software y videojuegos de 1981 a mediados de los 90, sobre hardware original o emulado.

Patrón común: compatibilidad, acceso directo al hardware, bajo consumo y comportamiento predecible. No es un reemplazo de Windows o Linux.

Marcar la diferencia entre “usar FreeDOS porque es antiguo” y “usar FreeDOS porque resuelve un problema actual”.

El caso de firmware es el más extendido: muchas utilidades de BIOS/UEFI siguen distribuyéndose como ejecutables DOS.

Vigencia

Límites y valor pedagógico

Balance

Desafíos del proyecto

  • Relevo generacional: pocos colaboradores con conocimiento profundo de modo real y ensamblador x86.
  • Hardware contemporáneo: los fabricantes reducen el soporte de Legacy BIOS en favor de UEFI puro.
  • Percepción pública: la asociación automática con obsolescencia dificulta reconocer sus usos industriales.

Valor pedagógico

  • Modelo simple para enseñar gestión de memoria.
  • Interrupciones y estructuras de control visibles.
  • Arranque completo y trazable.
  • Menos capas conceptuales que un sistema moderno.

Compatibilidad: en equipos muy nuevos puede requerir modo legacy, un hipervisor o un emulador, según las instrucciones disponibles del procesador.

Valor real: FreeDOS permite ver el recorrido de una instrucción y el movimiento de datos dentro del circuito informático sin la complejidad de un sistema multitarea moderno.

No ocultar las limitaciones: el proyecto depende de trabajo voluntario y el soporte de arranque legacy se reduce.

El valor pedagógico es el argumento más fuerte para esta materia: el sistema es pequeño, pero internamente coherente.

Virtualización

Virtualización y emulación

DOSBox-X · QEMU

Ambas permiten ejecutar otro sistema, pero no hacen lo mismo. La diferencia está en si comparten la arquitectura del host o si la simulan.

Sistema invitado
Hipervisor
Hardware del host

Qué hace

Ejecuta varias máquinas virtuales sobre los mismos recursos. Requiere instrucciones de virtualización del procesador: Intel VT-x o AMD-V.

El hipervisor puede ser de tipo 1 (cerca del hardware) o de tipo 2 (sobre un sistema operativo).

Ejemplos

  • VirtualBox: tipo 2.
  • KVM: tipo 1 integrado en Linux.
  • QEMU + KVM: alto rendimiento.

Cuándo usarlo

  • VPS y cloud: AWS, Azure, DigitalOcean.
  • Laboratorios, DevOps y CI/CD.
  • Cuando se busca el mayor rendimiento nativo posible.
Aplicación invitada
Sistema invitado
CPU, RAM, BIOS y dispositivos emulados
Traducción / interpretación
Hardware del host

Qué hace

Recrea un hardware completo en software: procesador, memoria, BIOS, sonido y red. Puede ejecutar una arquitectura distinta a la del host.

Traduce cada instrucción y usa buffers en memoria; por eso consume más recursos que la virtualización.

Ejemplo: DOSBox-X

DOSBox-X emula el entorno necesario para ejecutar DOS y software de 16 bits. Es la opción más directa para las prácticas de DEBUG, NASM y OpenGEM.

QEMU: emular o virtualizar

QEMU no es solo un emulador. Puede emular hardware completo con TCG o acelerar con KVM cuando el host y el invitado comparten arquitectura. En la práctica usamos TCG porque emulamos un Pentium con 32 MB de RAM.

Cuándo usarlo

  • Arquitecturas cruzadas: Android en Windows.
  • Preservación y prueba de sistemas antiguos.
  • Ingeniería inversa y depuración de firmware.

La diferencia clave: el virtualizador comparte la ISA del host; el emulador simula otra arquitectura. Si el software es de 16 bits y el host es x86 moderno, igualmente se usa emulación por el entorno de hardware y el arranque.

DOSBox-X permite montar imágenes, discos y carpetas del host sin instalar FreeDOS en el equipo real. QEMU permite ver el arranque completo y el particionado de un disco virtual; conviene usar cada uno para lo que muestra mejor.

Prácticas

Elegí la herramienta y seguí la guía

DOSBox-X / QEMU

Las dos herramientas permiten ejecutar FreeDOS, pero resuelven el laboratorio de forma distinta. Elegí una y seguí sus instrucciones; las cuatro prácticas detalladas de DOSBox-X quedan disponibles más abajo.

Cuándo elegir DOSBox-X

  • Querés montar carpetas del host como unidades DOS.
  • Vas a usar DEBUG, NASM y OpenGEM con la guía paso a paso.
  • Buscás una configuración rápida, sin instalar un sistema completo.

Secuencia general

  1. Crear un disco virtual de 50 MB con imgmake.
  2. Montarlo como C: y la carpeta del host como D:.
  3. Copiar FreeDOS, KERNEL.SYS y COMMAND.COM.
  4. Escribir el sector de arranque con sys c:.
  5. Instalar NASM, configurar PATH y verificar con nasm -v.

Las cuatro prácticas

Consejo de estudio: hacé primero la práctica 1 y volvé a las diapositivas de arranque, FAT y MCB cada vez que un comando no cierre. Las prácticas están pensadas para leer el sistema, no solo para copiar comandos.

Qué vamos a hacer: instalar QEMU, crear un disco virtual, instalar FreeDOS desde la LiveCD, preparar las particiones y sumar aplicaciones desde el BonusCD. Cada comando lleva un comentario con el “qué” y el “por qué”.

01

Instalar QEMU y las utilidades de disco

sudo apt update
sudo apt install --no-install-recommends qemu-system-x86 qemu-utils

Por qué: qemu-system-x86 provee el emulador de la máquina y qemu-utils aporta qemu-img, la herramienta para crear y administrar discos virtuales. --no-install-recommends evita paquetes opcionales que no necesitamos para el laboratorio.

02

Crear el disco virtual

# -f: formato de disco
# 200M: tamaño máximo del disco
# qcow2 crece dinámicamente: empieza chico y ocupa más a medida que se escribe
qemu-img create -f qcow2 disk0.qcow2 200M

Qué devuelve: fmt confirma el formato; cluster_size es el bloque de almacenamiento (64 KB por defecto); size es el tamaño total; lazy_refcounts y refcounts_bits son metadatos internos que conviene dejar por defecto. compression_type indica si el contenido está comprimido.

03

Descargar y descomprimir las imágenes

# Traer los ZIP desde Descargas a la carpeta de trabajo
mv ~/Descargas/FD14-LiveCD.zip .
mv ~/Descargas/FD14-BonusCD.zip .

# Separar cada imagen en su propia carpeta
unzip FD14-LiveCD.zip -d live
unzip FD14-BonusCD.zip -d bonus

# Limpiar los ZIP una vez extraídos
rm FD14-LiveCD.zip FD14-BonusCD.zip

Por qué: mv mueve los archivos; unzip -d extrae en un directorio distinto para no mezclar la LiveCD con el BonusCD; rm elimina los comprimidos originales. Si la ruta tiene espacios, usá comillas: mv "$HOME/Descargas/FD14-LiveCD.zip" .

04

Arrancar el instalador de FreeDOS

# -m 32: 32 MB de RAM para la máquina virtual
# -cpu pentium: emula un procesador Pentium compatible
# -accel tcg,thread=multi: acelera la emulación por software con varios hilos
# -hda disk0.qcow2: disco principal donde se instalará FreeDOS
# -cdrom: imagen óptica de instalación
# -boot d: arranca desde el CD-ROM
qemu-system-i386 -m 32 -cpu pentium -accel tcg,thread=multi \
  -hda disk0.qcow2 -cdrom live/FD14-LiveCD.iso -boot d

Antes de ejecutar: verificá el nombre exacto del archivo .iso dentro de live/. Si se llama distinto, ajustá la ruta de -cdrom.

05

Particionar, reiniciar y formatear

# Dentro del instalador, crear:
#   1. una partición primaria para el sistema operativo
#   2. una partición extendida que ocupe el resto del disco
#   3. una unidad lógica dentro de la extendida
fdisk

# Reiniciar desde el menú Machine > Reset y luego formatear:
format c:
format d:

Por qué: la partición primaria alojará el sistema operativo. La extendida funciona como un contenedor que permite crear unidades lógicas; es una forma de ordenar el resto del espacio y de mantener un índice en la tabla de particiones. El formateo escribe el boot sector, las FAT y el directorio raíz: el contenedor deja de ser una caja de bits y pasa a tener un sistema de archivos.

06

Arrancar desde el disco instalado

# -boot c: ahora arranca desde el disco, no desde el CD
qemu-system-i386 -m 32 -cpu pentium -accel tcg,thread=multi \
  -hda disk0.qcow2 -boot c

Qué vas a ver: el menú de FDCONFIG.SYS, donde se elige la administración de memoria y los controladores de bajo nivel. Las familias más comunes son JEMM386 (clásica, memoria superior y EMS desactivada por defecto) y JEMMEX (dos en uno: memoria extendida, memoria superior y compatibilidad con juegos viejos).

07

Instalar aplicaciones desde el BonusCD

# Levantar la máquina con el BonusCD además del disco ya instalado
qemu-system-i386 -m 32 -cpu pentium -accel tcg,thread=multi \
  -hda disk0.qcow2 -cdrom bonus/FD14-BonusCD.iso -boot c

Por qué: el disco ya tiene FreeDOS; el CD aporta los paquetes. Dentro de FreeDOS, la letra de la unidad óptica suele ser E:; verificá con dir e:\.

# xcopy copia archivos y estructura de directorios
# /i asume que el destino es un directorio
# /y evita la pregunta de confirmación
xcopy "e:\packages\gui\opengem.zip" "c:\applications\" /i /y
xcopy "e:\packages\edit\pico.zip" "c:\applications\" /i /y
xcopy "e:\packages\devel\nasm.zip" "c:\applications\" /i /y
# Descomprimir cada paquete en su propia carpeta
cd c:\applications
unzip opengem.zip -d gem
unzip pico.zip -d bin
unzip nasm.zip -d nasm

Qué anotar: mientras descomprimís, registrá el .exe o .bat que lanza cada programa y su ubicación. Las rutas típicas quedan así:

c:\applications\nasm\devel\nasm\nasm.exe
c:\applications\gem\gui\opengem\gem.bat
c:\applications\bin\pico.exe
# Crear lanzadores en c:\freedos\bin para poder llamarlos desde cualquier ruta
echo @c:\applications\nasm\devel\nasm\nasm.exe %1 %2 %3 %4 %5* > c:\freedos\bin\nasm.bat
echo @c:\applications\bin\pico.exe %%* > c:\freedos\bin\pico.bat

OpenGEM necesita una configuración especial: se mapea una unidad temporal con swsubst, se entra en ella, se lanza gem.bat y al salir se restaura la unidad original.

copy con c:\freedos\bin\gem.bat

@echo off
swsubst o: c:\applications\gem\gui\opengem
o:
cd \
call gem.bat
c:
cd \
swsubst /d o:

Para cerrar copy con, presioná Ctrl+Z y luego Enter.

Por qué: los lanzadores de c:\freedos\bin quedan en el PATH y permiten ejecutar los programas desde cualquier carpeta. Para GEM, swsubst crea una letra de unidad temporal que apunta a la carpeta de la interfaz gráfica, de modo que sus rutas internas funcionen sin mover archivos.

QEMU frente a DOSBox-X: QEMU instala un sistema completo y permite ver el arranque, las particiones y el disco real emulado. DOSBox-X es más directo para las prácticas de herramientas. Usar las dos cosas da una comprensión más completa: QEMU para el sistema, DOSBox-X para el software.

La pestaña QEMU está pensada para acompañar la instalación en vivo. No dictar todos los comandos: mostrar la lógica de cada etapa y dejar que los alumnos resuelvan las rutas.

Si el grupo ya tiene DOSBox-X funcionando, usar QEMU como demostración del arranque completo y reservar la práctica individual para DOSBox-X.

DOSBox-X · Práctica 1

Preparar el entorno DOSBox-X

Disco virtual

Crear un disco virtual de 50 MB, instalar FreeDOS y dejar NASM disponible en el PATH.

Secuencia

  1. Crear la imagen de disco con imgmake.
  2. Montarla como C: y montar la carpeta del host como D:.
  3. Copiar FreeDOS, KERNEL.SYS y COMMAND.COM.
  4. Escribir el sector de arranque con sys c:.
  5. Copiar NASM y configurar PATH.
  6. Verificar con nasm -v.

Antes de ejecutar: los comandos se escriben desde la unidad Z: de DOSBox-X. Ajustar las rutas del host a la ubicación real de la carpeta C:\FreeDOS.

imgmake C:\FreeDOS\freedos.img -t hd -size 50

imgmount c C:\FreeDOS\freedos.img -t hdd
mount d C:\FreeDOS
d:
xcopy d:\freedos c:\freedos /s /e
copy d:\kernel.sys c:\
copy d:\command.com c:\
c:
sys c:
md c:\nasm
d:
cd NASM-2~1.05R
xcopy *.* c:\nasm /s /e
c:
set PATH=%PATH%;C:\NASM
nasm -v

No eliminar -fs fat sin motivo: en el montaje de la imagen conviene dejar que DOSBox-X lea la geometría real de la partición.

Si sys c: falla, revisar que KERNEL.SYS y COMMAND.COM estén en la raíz de C: y que la imagen esté montada como disco duro.

DOSBox-X · Práctica 2

Programa con DEBUG

hola.com

Ensamblar a mano un programa que imprime Hola Mundo!, calcular su tamaño y escribirlo en disco.

C:\> debug
-a 100
xxxx:0100 mov ah, 09
xxxx:0102 mov dx, 0109
xxxx:0105 int 21
xxxx:0107 int 20
xxxx:0109
-e 0109 'Hola Mundo!$'
-r cx
:15
-n hola.com
-w
-q

Por qué empieza en 100h

DEBUG reserva los primeros 256 bytes para el PSP: parámetros de consola, salida de emergencia y tablas temporales. El código comienza después.

Tamaño total

CX = 15h = 21 bytes decimales: 9 bytes de código + 12 bytes de la cadena.

0100B4 010109 0102BA 010309 010401 0105CD 010621 0107CD 010820 010948 010A6F 010B6C 010C61 010D20 010E4D 010F75 01106E 011164 01126F 011321 011424
Código · 9 bytes Cadena ASCII · 12 bytes Total: 21 bytes = 15h

Desglosar el tamaño: mov ah,09 ocupa 2 bytes; mov dx,0109 ocupa 3; int 21 2; int 20 2. Total código: 9. La cadena 'Hola Mundo!$' ocupa 12.

int 20 es la salida histórica. En código nuevo conviene INT 21h / AH=4Ch, pero DEBUG acepta la forma corta.

DOSBox-X · Práctica 3

Ensamblador NASM

.COM

El mismo programa, ahora en ensamblador: directiva org 100h, impresión por INT 21h y salida por 4Ch.

org 100h

section .text
  mov ah, 09h
  mov dx, msg
  int 21h

  mov ah, 4Ch
  mov al, 00h
  int 21h

section .data
  msg db 'Hola Mundo!', 0Dh, 0Ah, '$'

Compilar y ejecutar

nasm -f bin hola.asm -o hola.com
hola.com

Qué hace cada bloque

  • AH=09h y DX=msg: imprimir cadena.
  • INT 21h: llamar al kernel.
  • AH=4Ch, AL=00h: terminar con éxito.
  • 0Dh, 0Ah: retorno de carro y salto de línea.
  • $: terminador de cadena para DOS.

Formato: org 100h y -f bin generan un .COM que se carga después del PSP. El programa no necesita un encabezado .EXE.

Si NASM no está en el PATH, ejecutar set PATH=%PATH%;C:\NASM o llamar al binario con ruta completa.

La directiva section .data funciona con el formato binario; el mensaje queda en el mismo segmento y mov dx, msg resuelve la dirección.

DOSBox-X · Práctica 4

Interfaz gráfica con OpenGEM

GUI sobre DOS

OpenGEM es una interfaz gráfica que se ejecuta sobre FreeDOS. No forma parte del kernel: es una capa de software que necesita sus propios archivos y drivers.

Preparación

  1. Montar la ISO FD14BNS.iso en el explorador del host.
  2. Extraer PACKAGES\GUI\opengem en C:\FreeDOS\GUI\opengem.
  3. Montar la imagen de FreeDOS y entrar a D:.
  4. Desmontar C: y montar la carpeta de OpenGEM como C:.
  5. Ejecutar gem.
imgmount d C:\FreeDOS\freedos.img -t hdd -fs fat
d:
mount -u c
mount c C:\FreeDOS\GUI\opengem
c:
gem

Rutas: si OpenGEM no inicia, verificar que la carpeta extraída sea la raíz montada en C: y que la unidad anterior se haya desmontado con mount -u c.

Diferenciar GUI de sistema operativo: OpenGEM es una aplicación que corre sobre DOS, igual que Windows 3.x corría sobre DOS.

Esta práctica sirve para mostrar que FreeDOS puede soportar interfaces gráficas, aunque el sistema base siga siendo de línea de comandos.

Cierre

Conceptos para retener

Repaso

Modelo de ejecución

DOS es monotarea y monousuario, con registros de 16 bits, direcciones de 20 bits y sin protección de memoria.

Almacenamiento

Un file system es índice + reglas. FAT encadena clústeres; NTFS y EXT agregan journaling y permisos.

Arranque

BIOS/UEFI → MBR/VBR → KERNEL.SYS → FDCONFIG.SYS → COMMAND.COM/FDAUTO.BAT → C:\>.

Interrupciones

La IVT es una tabla de despacho. INT 21h expone los servicios del kernel; los TSR esperan su interrupción.

Consultas

Repasar los cuatro bloques y abrir preguntas. Si queda tiempo, ejecutar MEM y comparar el mapa con la diapositiva de memoria.
